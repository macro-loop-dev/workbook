A real pull request to FloatNote

Someone else's repo, someone else's rules, and a change that ships to real users.

Why this chapter exists

Everything so far happened in a repo built for you to learn in. FloatNote is William's product: a notepad where any line of maths quietly gets its answer down the right edge. It has users, a release process, a desktop app, and a few thousand lines of code with rules you did not write. Contributing to it is the point of the whole course, and the way you do it is the same loop you have run eleven times: branch, small change, test, commit, PR, review, merge.

What is new is the order of reading. Before you change anything, you read what the project says about itself, you run its checks on a clean copy so you know what "working" looks like before you touch it, and you pick a change small enough to review in a minute.

A story

FloatNote, src/docs.test.ts, August 2026

You met this file in chapter 8: the guard that fails if any example on FloatNote's docs page stops computing, written after the page once lied. Today you are on the other side of it. If your new example does not compute, the guard refuses your PR before William sees it. That is not the project being difficult. It is the reason your PR can be merged in an afternoon by someone who did not watch you write it.

What you will do

  • Get a working copy of FloatNote and run its checks before changing anything.
  • Read its rules: CLAUDE.md and the invariants in docs/HANDOFF.md.
  • Pick one change from a short menu and make it, with its test.
  • Open the PR, get it reviewed, get it merged.
  • Delete the reviewer's notes from your own repo. It is yours now.

Do it

  1. Accept the invitation. William adds you as a collaborator on macro-loop/floatnote. The invitation arrives by email and at github.com/notifications. The repo is private, so there is no fork: you work on a branch in the real repo, which is why branch names and small commits matter more here.
  2. Clone it and turn on the hook. 
    gh repo clone macro-loop/floatnote ~\dev\floatnote
Set-Location ~\dev\floatnote
git config core.hooksPath .githooks
npm ci

    npm ci installs exactly what the lockfile says and takes a few minutes the first time; one package downloads from a non-npm address, so it needs the internet once. The same gitleaks hook as your repo, in the same place.

  3. Run the checks on a clean copy, before touching anything. 
    npm run typecheck; npm run lint; npm test

    Three green results. The tests take a while: there are about thirty suites and one of them starts a small local server on purpose. Slow is not broken. Write down how long it took. If anything is red on a clean checkout, stop and tell William; that is not yours to fix and it is worth knowing.

  4. Read the rules. Open CLAUDE.md at the root. It is short and says only what you would otherwise guess wrong. Then docs/HANDOFF.md: read the module table once, and the numbered invariants twice. An invariant is a rule the whole codebase depends on; breaking one is the kind of change that gets a PR closed, not commented on.

    Two things from CLAUDE.md apply to you today: never introduce a .env file, and never run npx tauri; the desktop build needs a toolchain you do not have and is verified by William before releases. Ignore the src-tauri folder entirely.

  5. Pick one change from the menu. All of these stay out of the two large files (engine.ts, editor.ts) that the invariants guard hardest. Choose the first one unless you have a reason not to.
    1. A new example in the docs. src/docs/07-units-tables.txt is a real FloatNote note shown on the docs page. Add one unit conversion line to the length list, then register it in src/docs.test.ts so the guard checks it forever.
    2. A copy fix on the landing page. landing/index.html, a single self-contained file. Find a sentence you would say better.
    3. A ranking case. src/fuzzy.test.ts tests which command comes first when you type a few letters. Add one eq(...) case that documents behaviour you checked by hand in the app.
    4. Ambitious: a settings toggle. A field in src/settings.ts (add only, never remove; the file explains why) and a row in src/app-settings.ts copying the lineNumbers pattern. Talk to William before starting this one.
  6. Branch, named for the change. FloatNote uses docs/, feat/, fix/ prefixes on branches the same way as on commits. 
    git switch -c docs/units-example
  7. Make the change (menu item 1 shown). In src/docs/07-units-tables.txt, under the line 6 ft + 2 inches in cm, add one line: 
    100 km in mi
    No full stop at the end: the guard treats a line ending in a full stop as prose, and prose must not compute. Check your line in the app: npm run dev, open http://localhost:1420, type it, and read the answer column. About 62.137.
  8. Register it with the guard. In src/docs.test.ts, find the two existing answers(...) lines and add yours below them: 
    answers("0.5 btc in usd");
answers("$500 in eth");
answers("100 km in mi");
    The string must match your docs line character for character; the test reports MISSING LINE otherwise. 
    npx tsx src/docs.test.ts; npm run lint

    One more test passes than before, and the lint is clean. If lint complains about a file you did not touch, do not run lint:fix on the whole repo: that reformats other people's lines and is the first review comment you would get.

  9. Commit and push. 
    git add src/docs/07-units-tables.txt src/docs.test.ts
git commit -m "docs: add a km to mi example to the units chapter, guarded"
git push -u origin docs/units-example
  10. Open the PR and write it for a stranger. FloatNote has no PR template, so bring your own: what changed, why, how you checked it. 
    gh pr create --title "docs: km to mi example in the units chapter" --body "What changed: one example line in 07-units-tables.txt and its answers() guard in docs.test.ts.`n`nWhy: the length list had no metric-to-imperial example.`n`nHow I checked it: typed the line in the app (62.137 mi); npx tsx src/docs.test.ts passes; lint clean."

    CI runs typecheck, lint, test and build, the same four you ran in step 3. Green in a few minutes.

  11. Review, change, merge. William reviews the way he would review anyone. Expect at least one comment. Change what he asks, push again, reply on the thread. When it is merged, pull main and delete your branch, and look at the docs page on app.floatnote.dev after the next deploy: your line is on it.

Check

Your PR is merged. git log --oneline -3 on FloatNote's main shows your commit. The three checks are green on a clean main after your change, same as before it.

What can go wrong

  • The README talks about ARM64 and a Rust toolchain. That is for the desktop build. Not yours; skip every step mentioning tauri.
  • npm test seems stuck. It is running about thirty suites in a row and one starts a local server. Give it the time it took in step 3 before deciding.
  • MISSING LINE from the docs test. Your string in the test and the line in the docs file differ: a space, a capital, a full stop.
  • computes nothing from the docs test. The calculator did not understand your line. Try it in the app; change the line, not the test.
  • An @ in your example fires a real request. Lines shaped like @weather are live in the docs page. Examples of tags must be wrapped in backticks; the guard checks this too.
  • Lint touched files you never opened. You ran lint:fix across the repo. git restore the files you did not mean to change; a PR should contain only its own idea.
  • Push rejected: protected branch. You committed on main. git switch -c docs/units-example carries the commit over; then git branch -f main origin/main puts main back.

Mark it done

  1. Tick chapter 11 on your live site. 12 of 12.
  2. One last line in Today I learned.
  3. Back in ~\dev\workbook: delete the reviewer's notes and the line that hid them from the AI. They were never secret; they were his. 
    git switch -c chore/its-mine
git rm -r for-william
Set-Content -Path .cursorignore -Value ""
git add .cursorignore
git commit -m "chore: remove the reviewer notes, this repo is mine now"
git push -u origin chore/its-mine; gh pr create --fill
    William approves it. It is the last review he is required to give.

Pair with William

William's review of the FloatNote PR is the checkpoint. There is no demo this time; the merge is the demo.

Then a separate conversation, not on the same day: what next. Your own idea, built the same way, on the same site, under Projects. The ladder is the same; only the thing being built changes.

Deliberately not in this chapter

No changes to engine.ts, editor.ts, main.ts or palette.ts: every one is guarded by invariants and one by research that was partly wrong. No desktop build, no release, no version bump. No "while I'm in here" changes. One slice.
