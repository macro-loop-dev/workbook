A domain of your own

Names are a lookup table that anyone can read and you can edit. Today you get a row in it.

Why this chapter exists

The .pages.dev address works, but it is Cloudflare's name with yours tucked inside. A domain is a name you rent by the year (example.com is one) and point wherever you like. The pointing is done by DNS, the Domain Name System: a public, world-wide lookup table from names to the numbered addresses computers actually use. Every website you have ever visited went through it in the first few milliseconds.

The name outlives this course. The site behind it will be rebuilt three more times before chapter 11; the name will not change, and it will be the one on your CV. That is also why William buys it, in the project's account, with the settings that stop it quietly expiring.

A story

FloatNote's DNS table, August 2026

The table for floatnote.dev has the rows you would expect: one for the app, one for the landing page. It also has rows called send and resend._domainkey. Those have nothing to do with the website. They let an email service called Resend send FloatNote's login codes and prove the emails are genuine. Same table, different job. Delete the wrong row while tidying up and the site is fine but nobody can log in. A DNS table serves more than the website, and you read a row before you touch it.

What you will do

  • Watch William register the name and see what was actually bought.
  • Ask your laptop what it knows about the name: nothing, at first.
  • Attach the name to the Pages project and watch Cloudflare write two rows.
  • Ask again, and read the new answer.
  • Send www to the bare name, and wait for the padlock.
  • Ship chapter 6 with a pull request that carries the live address.

Do it

  1. Choose the name, before the session. Short. Easy to say out loud on the phone. Letters, maybe one hyphen. A name you would be happy with at 25, so probably yours, not a joke. In the Cloudflare dashboard (menus as of 2026-09-02; William's click paths are in his for-william/dashboard-clicks.md): Domain Registration → Register Domains, type the name, see which endings are free. Do not buy yet.
  2. Ask before. In PowerShell 7, with your real name in place of the placeholder, here and in every command below: 
    Resolve-DnsName <your-domain>

    A red error: DNS name does not exist. Your laptop asked the lookup table and there is no row. Remember what this looks like; you will see it again whenever you mistype a name.

  3. William registers it. His screen, his card, his name on the registration if you are under 18. In the project account, not his personal one: the name and the Pages project must live in the same account to be joined. He turns on auto-renew (so it does not expire while nobody is looking) and WHOIS privacy. WHOIS is the public list of who owns which name; privacy puts the registrar's address there instead of a home address. The company that sells names is a registrar; here that is Cloudflare too.

    What was bought: one year of the right to say where this name points. Not the name forever. That is what renewal is.

  4. Read the empty table. Click the new domain, then DNS → Records. Five columns: Type, Name, Content, Proxy status, TTL. Zero rows, or nearly. On the domain's overview page, find the two nameservers, ending in ns.cloudflare.com: the computers that answer questions about your name. Because Cloudflare is both registrar and DNS host, they are already set. With another registrar you would copy those two names across by hand, and that step is where most "my domain does not work" stories start.
  5. Attach the name to the site. Workers & Pages → workbook → Custom domains → Set up a custom domain. Type the bare name, Continue. It shows the row it is about to write; Activate domain. Then do it again for www.<your-domain>.

    Two entries on the Custom domains page, each saying Initializing or Verifying. Leave them.

  6. Read the table again. DNS → Records.

    Two rows of type CNAME: one named your bare domain, one named www, both with the .pages.dev address in the Content column, both with an orange cloud (proxied). A CNAME row means "the answer for this name is whatever the answer for that other name is". The bare name and www are two different names to DNS, which is why there are two rows. Proxied means Cloudflare answers with its own addresses and passes visitors through, which is what makes the padlock in step 9 possible.

  7. Ask after. 
    Resolve-DnsName <your-domain>
Resolve-DnsName www.<your-domain>
Resolve-DnsName <your-domain> -Type NS

    The first two answer with a small table: two rows of type A, each with an address like 104.21.x.x or 172.67.x.x. Those are Cloudflare's front door, not your files. The third lists the two nameservers. If the first command still says "does not exist", your laptop remembered the old answer: run ipconfig /flushdns and ask again.

  8. Send www to the bare name. Rules → Redirect Rules → Create rule → pick the template Redirect from WWW to Root → Deploy. It is a 301, the number for "moved permanently", which browsers remember. Chapter 5's story is the reason: one site, one address, or the browser keeps two separate memories of it.
  9. Wait for the padlock. Back on Custom domains, refresh until both say Active. The s in https means the connection is encrypted, and for that the server needs a certificate: a signed statement that it is allowed to speak for this name. Cloudflare requests one for you; it can take fifteen minutes. Then open https://<your-domain>.

    Padlock in the address bar. The Workbook, saying 6 of 12 done. Now type www.<your-domain>: the address bar changes to the bare name on its own.

  10. Phone. Same address, typed by hand, on mobile data rather than Wi-Fi so it goes through a different lookup table.

    6 of 12. If your phone says the name does not exist, its table has not heard yet: the waiting in the title, and the first gotcha.

Check

In PowerShell 7, all three Resolve-DnsName commands from step 7 answer with a table and no red. In a browser: https://<your-domain> shows the padlock and 6 of 12 done; www. in front lands on the bare name; and the old .pages.dev address still works, because it is the same site with two names.

What can go wrong

  • Still "does not exist" an hour later, on one device. Every lookup table between you and Cloudflare keeps answers for a while, including "no such name". ipconfig /flushdns on the laptop; on the phone, switch between Wi-Fi and mobile data. Otherwise go outside for an hour: changes reach the whole world in minutes to a day, which is called propagation. Resolve-DnsName <your-domain> -Server 1.1.1.1 asks Cloudflare directly and skips every cache in between.
  • An email asks William to "verify your email address" for the domain. It is real, and it is the one email he must not ignore: an unverified registration is switched off after fifteen days. Tell him.
  • Custom domains says the name is not in this account. It was registered under the wrong login. Moving a name between accounts is a chore; better to notice now, before any rows exist.
  • Initializing or Pending for more than fifteen minutes. Check the CNAME row exists and is proxied (orange cloud). If it does, remove the custom domain and add it again; that restarts the certificate request.
  • The browser says "not secure" or shows a certificate warning. The certificate is not issued yet. Wait; do not click through. A warning you learn to click through is a habit that will hurt you on someone else's site.
  • The bare name works but www does not, or the other way round. They are two names and each needs its own row. Step 5 was done once instead of twice.
  • You chose a .dev name and http:// never works. By design: browsers refuse plain http for every .dev name. Type https://, or nothing at all.

Mark it done

  1. A branch: 
    git switch -c chapter-6
  2. In index.html, on the data-chapter="06" line, change data-status="todo" to "done".
  3. Commit, push, and open the PR with the live address in its description. From now on every PR says where the result can be seen: 
    git add index.html; git commit -m "docs: mark chapter 6 done"; git push -u origin chapter-6
gh pr create --title "docs: mark chapter 6 done" --body "Live at https://<your-domain>"
  4. Wait for William's approval. Merge, delete the branch on GitHub, watch the deployment, then open https://<your-domain> on the laptop and the phone.

    7 of 12 done, at your name. That is the proof for this chapter: not the .pages.dev address, yours.

  5. Tidy up: 
    git switch main; git pull; git branch -d chapter-6
  6. One line in Today I learned, at the top. The date the name renews is a good line.

Pair with William

You will: read the DNS table aloud, row by row, saying what each row is for. Then: why are there two CNAME rows, and what would stop working if you deleted one?

William will: confirm the domain is in the project account, auto-renew is on, WHOIS privacy is on, and SSL/TLS is set to Full (strict); then write the renewal date into his notes. He will also open the .pages.dev address next to your name: one site, two names, and only one of them is on your CV.

Deliberately not in this chapter

No email at your domain, although the table could carry it; the story shows what that looks like. No other record types beyond reading them: A, MX and TXT rows exist and you will meet them when you need them. No moving the name to an account of your own yet; ask at chapter 10, when the repo is renamed to match it.
