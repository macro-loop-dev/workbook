Push and open a pull request

A remote is a backup and a conversation.

Why this chapter exists

Your four commits exist on one hard drive. A remote is a second copy of the repo on another computer; here GitHub, which your repo already calls origin. Pushing copies commits there. That is the backup half.

The conversation half: a remote is also where two people change the same files without overwriting each other. You put your change on a branch, a named line of commits that starts from main and can be joined back later. You open a pull request (PR), a page on GitHub that shows the branch's diff and asks for it to be joined into main. Someone reads it, comments, approves. Joining is a merge. Today you go both directions: your first PR, and your first review of someone else's.

A story

William's dev-setup repo, HANDOFF.md, 2026-08-24

The handoff file for William's setup repo lists five things that must never break. Number two: "No secret in the repo, ever. The gitleaks pre-commit hook catches the key-shaped cases and CI re-runs it, because hooks are local and bypassable." Chapter 3's hook lives on your laptop and one flag turns it off. The workflow file in this repo, .github/workflows/gates.yml, carries a comment: "This is the copy that cannot be skipped." Today you watch it run.

What you will do

  • Make a branch, mark the chapter done on it, push it.
  • Open a pull request and watch the first automatic check run.
  • Review a pull request William opened for you: read, approve, merge.
  • Push a second commit and see the PR update; then survive one review comment.

Do it

  1. Start clean, on main. Terminal in Cursor, inside ~\dev\workbook: 
    git status; git log --oneline -1

    "working tree clean", and the commit shown is marked (HEAD -> main). Uncommitted changes: commit them first, the chapter 3 way.

  2. Make a branch. Names are lower-case letters, digits and hyphens; in this course, chapter-N. 
    git switch -c chapter-4; git log --oneline -1

    Switched to a new branch 'chapter-4', and the top commit is now marked (HEAD -> chapter-4, main): one commit, two names. A branch is only a name until you commit on it.

  3. Mark chapter 4 done, on the branch. Change the attribute on the data-chapter="04" line, by hand or by asking. Then: 
    git diff; git add index.html; git commit -m "docs: mark chapter 4 done"

    One red line, one green; the logo and no leaks found; then [chapter-4 ...] docs: mark chapter 4 done. The name in the brackets changed.

  4. Push the branch. 
    git push -u origin chapter-4

    Some counting lines, then:

    remote: Create a pull request for 'chapter-4' on GitHub by visiting:
remote:      https://github.com/macro-loop-dev/workbook/pull/new/chapter-4
remote:
To https://github.com/macro-loop-dev/workbook.git
 * [new branch]      chapter-4 -> chapter-4
branch 'chapter-4' set up to track 'origin/chapter-4'.

    If a window asks you to sign in to GitHub, choose "Sign in with your browser". Once.

    -u pairs this branch with origin/chapter-4, so from now on git push alone is enough. Five commits now exist on two computers. Chapter 3's four came along: a push sends every commit the remote does not have yet.
  5. Open the pull request. gh is the GitHub command from chapter 0. 
    gh pr create --fill
    Creating pull request for chapter-4 into main in macro-loop-dev/workbook

https://github.com/macro-loop-dev/workbook/pull/7

    Your number will differ. Read the first line: from chapter-4, into main. --fill makes the title from the branch name ("chapter 4") and the description from your commit messages. The web way is gh pr create --web: the same form in the browser, with the repo's description template already in it. Either works.

  6. Read your own PR, then write it for a reader. 
    gh pr view --web
    The description lists five commits, four from chapter 3: a PR is "everything on this branch that main does not have", and GitHub's main never got those. Files changed is the diff of all five together. Now the three dots on the description → Edit: above the list, paste the three headings from .github/pull_request_template.md (What changed, Why, How I checked it) and answer each in one line. Save. The reader is William.
  7. Watch the check. Back in the terminal: 
    gh pr checks --watch

    One row named secrets: pending, then after half a minute or so pass, and "All checks were successful".

    This is CI, continuous integration: on every push, a computer at GitHub clones your branch and runs the checks listed in .github/workflows/gates.yml. Today that is gitleaks over every commit, the same scan as your hook, on a machine you cannot switch off. Your first green check. The PR page shows it next to a yellow "Review required": main is protected, and William must approve before anything joins it.
  8. Your first review. William opened a PR yesterday adding one Library item. Find it, read its diff: 
    gh pr list

    A row like #6 Library: <title> share/<slug> above yours. Use its number below.

    gh pr diff 6

    One green line in library/index.html: a new <li data-added="..." data-seen="no"> at the end of a section.

    Ask what a reviewer asks: one line? the shape the comment on line 29 of library/index.html shows? does the link open? is data-seen no? If all yes: gh pr view 6 --web, then Files changed → Review changes → Approve → Submit review; then Conversation → Merge pull request (it must say Create a merge commit) → Confirm merge. Delete the branch if offered: the commits are in main, the name is not needed. The terminal way, for later: gh pr review 6 --approve; gh pr merge 6 --merge. If something is wrong, Request changes instead, and say what.
  9. See what moved where. 
    git fetch origin; git log --oneline --all --graph

    A drawn graph. origin/main is now on a commit called Merge pull request #6 ...; your chapter-4 line branches off below it; your laptop's main has not moved. fetch downloads without changing your files. Do not git pull today: your main holds chapter 3's commits that GitHub's does not, and a pull cannot line the two up until your PR merges in chapter 5. William's item is on GitHub now, and on your laptop after that.

Check

gh pr status shows your PR under "Current branch" with "Checks passing". On GitHub, your PR is open with a green check and William's is purple, "Merged". git branch --show-current prints chapter-4. Your browser says 5 of 12 done; index.html on GitHub's main still says 0 of 12. Both are true. Chapter 5 makes them agree.

What can go wrong

  • ! [remote rejected] main -> main (protected branch hook declined), with GH006. You pushed main directly. That is the protection working: main only accepts merges from pull requests. Make the branch and push that.
  • Everything up-to-date and the PR has no commits. You committed on main, not chapter-4; git log --oneline --all --graph shows it. Ask William: the fix is three commands and easy to get wrong alone.
  • gh tells you to run gh auth login. This terminal is not logged in. gh auth status, then chapter 0's login step.
  • A "Sign in to GitHub" window at push time. Git Credential Manager. Choose the browser option; never a password, GitHub does not accept one for pushes.
  • The PR says "into" something other than main. Close it on GitHub and run gh pr create --fill --base main.
  • Branch name typo. Before pushing, git branch -m chapter-4 renames it. After pushing, tell William; it is a rename on both sides.
  • The check turned red. Details shows a log ending in a Finding: block like chapter 3's: a secret-shaped string is in some commit. Do not pile on more commits; ask William.

Mark it done

The attribute edit is already in your PR. Three things remain.

  1. One line in Today I learned, at the top. Commit it on the branch and push; no -u this time. 
    git add notes/til.html; git commit -m "docs: til for chapter 4"; git push

    Refresh the PR page: six commits, and the check is running again. That is the loop for the rest of the course: commit, push, the PR updates, the checks re-run.

  2. At the checkpoint William leaves one comment asking for one change. Make it, commit with a docs: message, push. Refresh: the comment now sits on an older version, and there is a new commit.
  3. William approves. Do not merge. Merging is chapter 5, because merging does something you have not seen yet.

Pair with William

You will: walk through your PR page: which commits it has and why four are older than today, what the green check ran and where, what "Review required" means. Then show William's merged PR and say what you checked before approving.

William will: review your PR for real: one comment on one line under Files changed; wait for you to fix it and push; then approve. He will explain .github/pull_request_template.md and why its three headings are in that order. He will not merge.

Deliberately not in this chapter

No merge of your own PR; that is chapter 5. No website: nothing you pushed today is visible anywhere except GitHub. No rebase, no squash, no force-push; if you meet those words somewhere, the answer for now is "not yet".
